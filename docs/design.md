# Jev Bookmarks 製品設計

## 目的

エージェントが「MFで登録済み口座を見たい」のような頼みごとを受けた時、普段使うChromeで実際に訪れたページから、開くべきURLを答える。役立ったURLだけを小さな電話帳へ残し、Chrome履歴から消えた後も再利用する。

検索・選択はURLを開く前の工程。ページ上の操作と、そのページで目的を達成できたかの判定は呼び出し元のBrowser Useが担う。

## 一回の利用

1. エージェントが自然文の目的を `find(goal)` に渡す。
2. 電話帳を先に探す。該当がなければ、Chromeの履歴をその時だけ読み、ローカルで候補を絞る。
3. Jevの `Choice` が候補IDか「該当なし」を選ぶ。製品はIDに対応する実在URLだけを返す。
4. エージェントが普段のChromeで開き、目的を進める。候補が外れた場合や該当がない場合は、結果を明示した上で通常のBrowser Useへ戻る。
5. 目的達成を観測した時だけ、エージェントが `record_result` に成功と最終URLを報告する。製品は目的とURLを電話帳へ保存する。開いただけ、読み込みに成功しただけ、Jevが高い確率を返しただけでは保存しない。

`find` はURLを答える一回の完結した呼出しであり、記録は利用後の別イベント。該当なしでも要求IDを返すため、その後の通常のBrowser Useで見つかった成功URLを電話帳へ残せる。呼び出し元の操作の成否を、URL選択時点で製品が推測しない。

## 責務と接続

| 部品 | 責務 |
| --- | --- |
| Chrome拡張 | 利用中のChromeプロファイルの履歴を正規の `chrome.history.search` で、要求時だけ読む。候補の絞り込みまでをChrome内で行う。 |
| Native Messaging host | Chrome拡張とローカルコマンドを接続する。ブラウザの内部DBを読まない。 |
| ローカルコマンド | `find`、`record_result`、電話帳の一覧と削除を提供する。Jevへの問合せと電話帳の永続化を所有する。 |
| TypeSafe Jev | 渡された有限個の候補について、目的に最も合うIDまたは「該当なし」を選ぶ。 |
| 呼び出し元のBrowser Use | 返されたURLを開き、実際の目的達成を観測して結果を返す。 |

Chrome拡張からホストへは `connectNative` を使う。拡張が起動したホストは同じユーザーだけが接続できるローカルIPCを開き、コマンドからの履歴要求を拡張へ渡す。macOS/LinuxではUnixソケット、Windowsでは名前付きパイプをOS適合部分として使い、呼び出し契約は共通にする。拡張がその場で履歴を検索して結果を返す。拡張IDを固定してホスト側で許可する配線と、Chrome起動中に要求を往復できることを、実装の最初の実機検証項目とする。Chromeと接続できない場合、電話帳の検索は使えるが、履歴検索は明示的な `CHROME_UNAVAILABLE` を返す。

## 候補の選び方

- 電話帳は保存済みの目的文・タイトル・URLのホスト名とパスを対象にする。候補が複数ならJevへ渡す。電話帳の候補が「該当なし」なら履歴へ進む。
- 履歴はURL・タイトル・訪問回数・最終訪問時刻を利用する。期間と件数は明示して取得する。`chrome.history.search` の期間省略時は直近24時間、件数省略時は100件となるため、省略値に頼らない。件数上限に達した期間は分割して取得し、候補生成前に取りこぼしを検出する。
- 履歴全件を保存せず、要求中だけChrome内で扱う。タイトル・ホスト名・パスの語の一致、訪問回数、最近の訪問を使って有限個に絞る。候補数と順位付けは、実履歴と試験用の頼みごとで計測して決める。
- Jevには目的文と候補のID・タイトル・ホスト名・パスを渡す。URLのクエリ文字列とフラグメント、履歴全件は送らない。戻ったIDをローカルの候補表で実URLに解決する。候補にないURLを生成させない。
- 候補が欠けていればJevには選べない。候補生成の再現率を実測し、足りない時だけサイト単位の段階選択などを追加する。「該当なし」をURLに読み替えず、そのまま返す。

Jevの `confidence` は候補間の確率分布の集中度であり、ページが役立つことの証明ではない。固定の成功閾値で自動保存しない。

## 電話帳

最小の記録は `目的文・実URL・タイトル・成功確認時刻`。一つのURLに複数の目的を関連づけられる。ローカルの製品専用データとして保存し、Gitには入れない。一覧と削除を提供し、履歴から消えたURLも明示的に削除するまで保持する。

`record_result` は `find` が返した要求ID、実際の最終URL、成功・失敗を受ける。成功時は、最終URLが要求後に履歴へ現れた `http(s)` URLであることを確認して記録する。目的達成の真偽はブラウザを操作したエージェントの観測に基づき、製品側が履歴だけから判定したことにはしない。失敗時は保存しない。最終URLが当初の候補と違う場合は、目的を達成した最終URLを記録する。ログイン用の一時URLなど、再利用できないURLを電話帳へ残さないための判定は実機で必要なケースを確かめて決める。

検索時の外部送信には候補の表示情報だけを使う。一方、電話帳には実際に開く完全なURLが残り得る。保存先のアクセス権と、一覧・削除の導線を実装時に確認する。

## 呼び出し契約

公開入口はエージェントが使えるローカルコマンドとし、結果は機械可読なJSONで返す。コマンド名や具体的なJSON schemaは接続検証後に固定する。

- `find(goal)` → `found {url, title, source, request_id}` または `no_match {request_id}`。
- `record_result(request_id, outcome, final_url)` → `recorded` または `not_recorded`。保存失敗はエラーとして返す。
- `list` / `forget` → 電話帳を確認・削除する。

履歴への権限はChrome拡張の `history`、ローカル連携は `nativeMessaging` に限る。電話帳に候補がない時にChromeが閉じていれば、履歴検索失敗を明示する。TypeSafeのAPIが失敗した時も候補を適当に一つ選ばない。

## 最初の実装範囲と受入

1. 利用中のログイン済みChromeから正規APIで履歴を取得でき、エージェントの一回の `find` 呼出しに返せる。内部SQLiteファイルへ直接依存しない。
2. 実履歴の約1万URLを対象にしても、Jevへ送るのは絞った候補だけで、全履歴の永続コピーを作らない。
3. 実際のMFの頼みごと数件について、目的ページが候補に入り、JevがURLまたは「該当なし」を返す。外れた場合は候補漏れとJevの選択違いを分けて測る。
4. 開いただけのページ、失敗したページは電話帳に入らない。成功を報告したURLは次回、Chrome履歴に存在しなくても見つかる。
5. Chrome切断、該当なし、TypeSafe障害、保存失敗をそれぞれ区別して表示する。電話帳の一覧と削除が使える。

最初の実装では履歴の常時監視、全履歴の同期、サイトマップ作成、サイト巡回、Browser Use本体の置換は行わない。候補漏れや誤選択が観測されたら、その実例を使って絞り込みと質問を直す。

## 未検証の点

- ログイン済みChromeへの拡張導入とNative Messagingの往復が、この端末で安定して動くか。
- 実履歴のタイトルとURLだけで、目的ページを十分に候補へ入れられるか。特に略称や、日本語の目的文と英語URLの組合せ。
- どのURLが再利用できるか。最終URLの確認方法と、クエリに状態を含むページの扱い。

これらは実装の前提として未確認であり、設計完了を動作確認済みとは扱わない。
